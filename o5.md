**Status: plan. Nothing here is implemented yet.**

Ship target: presentable tomorrow, written blind, first hardware contact is game
time. The electronics are unreliable today and will be unreliable on stage. This

## 1. The game

1. Operator opens `/game` and hits **New game**.
2. The site deals a random *level but sharp* position (≤ 8 pieces, engine eval
   ≈ 0.00, one move holds the balance) and shows it big, with real piece glyphs.
3. Two humans build that position on the board. Squares still needing a piece
   glow amber; squares with one glow white.
4. When occupancy matches and holds, the game **auto-starts** after a 3-2-1
   countdown. If detection is unhappy, **Start** is pressed. That button is
   always present and always works.
5. Five moves each (10 plies), with one instruction on screen throughout:
   **captured pieces go off the board** — a captive parked on an empty square
   reads as an unexplained piece and downgrades that ply to a prompt.
   The board reads each move off the sensors;
   whenever it can't, the screen asks a one-tap question instead.
6. Stockfish evaluates the final position. Whoever gained ground from 0.00 wins.
   The eval bar has narrated it the whole time, starting dead centre.

~3 minutes per game. Between games the board is untouched — its current debug
behaviour is what you get when no lighting command has been sent.

## 2. The failure ladder

Every capability degrades along a fixed path. Nothing above the **dead** column
is load-bearing; the demo script must survive the whole right-hand column.

| capability | works | degraded | dead |
| --- | --- | --- | --- |
| move input | auto-detected from sensors | prompt with 2-3 candidates, one tap | every move clicked on the website |
| setup check | auto-start on occupancy match | per-square diff on screen, Start button | Start button |
| square lighting | amber-needed / white-placed guidance | silently absent | website highlights (always on) |
| turn indicator | edge bar | — | website banner (always on) |
| eval bar | edge bar | — | website bar (always on) |
| eval itself | Stockfish | material count, labelled as such | admin decrees the number |
| result | final deep eval | material verdict | admin decrees the winner |

Plus four rules that shape the code:

- **Nothing blocks.** No await on hardware, no await on the engine. Every
  external call has a timeout and a fallback.
- **Every failure is named.** A `degraded: []` list rides on every state
  broadcast and renders as amber chips. "The system knows what's broken" beats
  "the system pretends".
- **Tunable at the venue.** Thresholds, bar mapping, board rotation and
  per-square masks are live-editable from the admin rail. No redeploy to fix a
  demo.
- **Don't touch the debug console.** `/` and the whole bring-up stack stay
  exactly as they are — they are the recovery tool when the electronics act up
  mid-demo. Puzzle mode is additive: new server module, new route, one hook.

## 3. Architecture

Game state is **server-authoritative**, in one tokio task. Reasons in order of
weight: a browser reload must not lose the game mid-demo; Stockfish has to be
server-side (the frontend is static assets on Cloudflare); the server already
ingests device events with gap detection and owns the command path; `shakmaty`
and a working UCI driver already exist in this repo, proven against real games;
and the projector, the operator's laptop and any phone all see one truth.

**One task, three producers, no shared lock.** `GameState` is owned by a single
tokio task fed by `mpsc::UnboundedSender<GameInput>`:

1. `device.rs:handle_event` — after the existing `ingest_event` call, forward
   occupancy-relevant `board.snapshot` / `sensor.changed` fields.
2. `client.rs:handle_inbound` — a new `Some("game")` arm, gated exactly like
   `command`.
3. `engine.rs` — eval results tagged with the `game_seq` they were requested at,
   so a stale eval for an undone position is dropped on arrival.

A `Mutex<GameState>` would be the obvious alternative and it is a trap: the
engine call is `async`, and holding a std mutex across that await is a deadlock
waiting to happen. The task owns the state, `state.rs` keeps a `watch`-style
copy of the last serialized snapshot so `init` doesn't round-trip the task, and
broadcasts go out through the existing `state.broadcast_msg`.

Broadcasts are **coalesced on a 100 ms tick** behind a dirty flag. Setup-phase
occupancy changes with every sensor event; a full snapshot per event is what
trips the existing `shed_lagged` path and starts dropping viewers.

Optional insurance (~30 lines): serialize the latest `game.state` to
`/tmp/arcade-game.json` on every phase change and restore it on boot, so a
server restart or redeploy mid-demo isn't fatal. Failing that, the rule is:
**do not redeploy during the demo.**

The frontend computes no chess rules. The server ships `legal_moves` with every
state, so click-to-move is "filter the server's list".

```
server/src/
  main.rs            + /api/game route, spawn the game task
  state.rs           + latest game snapshot for init
  client.rs          + dispatch "game" actions
  device.rs          + one call in handle_event() → game_tx.send(...)
  game/mod.rs        the task: state machine, transitions, view()
  game/observe.rs    occupancy / polarity / known tracking from the event stream
  game/infer.rs      the move matcher  ← pure, unit-tested, no I/O
  game/positions.rs  position loading + embedded fallback
  game/engine.rs     Stockfish UCI subprocess + material fallback
  game/paint.rs      board frame composition → device commands (capability tiers)
tools/fake-board.py  fake device speaking the real /board protocol
frontend/src/routes/game/+page.svelte
frontend/src/lib/game/*.svelte
```

## 4. Hardware truths that shape everything

All verified against the firmware, not assumed. Read before designing any
lighting or detection.

**Sensing.** Each square is a hall sensor behind two 8-channel muxes into a
10-bit ADC. A full 16-square scan is ~16 ms; a change needs 3 consecutive
agreeing scans, so **transitions land ~50 ms after the physical event**.
Classification (`firmware-atmega/src/sensors.cpp:136`):

- `positive` — filtered ≥ baseline + 70 counts
- `negative` — ≤ baseline − 70
- `uncertain` — **only reachable from an occupied state** (`sensors.cpp:146`
  requires `state != kEmpty`), when the reading falls between ±42 and ±70. This
  is the piece-being-lifted signal, and it never fires on an empty square.
- `empty` — otherwise

Polarity is a property of how the magnet was glued into that piece: **random per
piece, stable while the piece is upright.** It carries no colour or type
information — but it is a free 1-bit fingerprint per piece, and §7 uses it as
**evidence, never truth**: the axial component of a dipole field reverses sign
beyond the magic angle, so a piece sitting off-centre can read *inverted*, and a
piece straddling two squares registers on the neighbour with the sign flipped. So
a matching polarity is confirmation; a mismatching one is **not** evidence against
anything, and neighbour reads ignore polarity entirely.

> ### ⚠ The `valid` trap
>
> `firmware-esp/src/network_manager.cpp:382` is
> `valid.add(q.online && state != kUncertain)`, and the snapshot maps
> `uncertain → 0`, the same value as empty.
>
> So in a `board.snapshot`, **`valid == false` means *either* the quadrant is
> offline *or* a piece is being lifted off that square right now.** Treating
> `valid == false` as "offline, assume it matches expectations" produces two
> concrete failures: autostart fires while a player is holding a piece (its
> square went uncertain, got assumed-occupied, and masked squares don't reset the
> stability timer), and capture detection loses its evidence (the victim square
> goes uncertain on the way out, exactly when you need to see it go empty).
>
> Discriminate with `online_node_mask` / `nodes[].online`. `valid == false &&
> node_online` is **uncertain**, not unknown. `sensor.changed` carries the real
> state string and needs no inference.

**Square LEDs.** `lighting.set` → UART `SET_SQUARES`, payload
`mask:u16, r, g, b, duration:u16`. The AVR does `override_mask_ = mask`
(`lighting.cpp:143`) — replace, not merge — with one colour, and
`bus_manager.cpp:142` fans out one frame per node. Therefore:

> **Each quadrant can display exactly one override colour at a time.** Two
> `lighting.set` calls with different colours clobber each other on any node
> they share. "Missing squares white, extra squares red" is not implementable
> today: squares 12 and 13 are both in node 1.

Squares *not* in the override mask show the sensor colour — green for positive
polarity, blue for negative (config keys 7/8). During a game that reads as
random noise, because polarity is random per piece. Setting **both keys to the
same value** makes "a piece is here" one consistent colour. `CONFIG_SET` already
exists on the AVR; only the ESP lacks a command to reach it, so one ESP-only
change buys polarity-independent piece display. It commits EEPROM (~240 ms), so
do it once per game, not per frame, and restore on abort.

**Edge bars.** 16 LEDs per board edge, built from two independent 8-pixel
half-bars owned by two different quadrants (`kEdgeStripPixels = 8`, `edge_a_` on
PE0, `edge_b_` on PE1). 4 sides × 16 = 64 edge pixels. Two problems:

1. **No command addresses them.** `render()` hard-paints both strips solid white
   whenever the bus is active; only `IDENTIFY` overrides them (amber, and it
   blinks the squares too). Bars need an AVR change — §9.
2. **The PE0/PE1 split depends on a hardware bodge** still listed under *Known
   Bring-up Requirements* in `docs/board.typ`, along with "determine quadrant
   rotation and edge-bar direction from assembled hardware". Which half-bar lands
   on which side is **unknowable until game time**, so the mapping must be
   editable live — not an env var, which means a redeploy at the venue.

`board_map.h::kEdgePixelForPosition` already encodes the LED9/LED8 transposition
along the bar and is currently unused. Use it.

**Bus budget.** One 38400-baud multidrop line, one outstanding transaction, an
8-deep ESP queue (`bus_manager.h:125`, `kQueueCapacity = 8`), and a 25 fps
`RENDER_WINDOW` the quadrants shift their strips inside. A full-board update is up to 4 enqueues ≈ 25-40 ms of wire time,
competing with event polling. **Rule: paint on state change only, plus a 1 Hz
re-assert, hard cap 5 frames/second.** Flooding the bus looks exactly like "the
board froze". Animate on screen, snap the hardware.

**Capability discovery.** An unknown UART message type returns error code `2`,
surfaced as `command.result status=rejected reason=node_error data={node,
code:2}`. The server discovers rich-lighting support **per quadrant by trying it
once** — no version parsing, works with mixed firmware across the four nodes.
This is what makes the whole firmware layer optional rather than a gamble.

**"Debug state" is not a mode.** `device.mode.set` only gates diagnostic log
verbosity (`diagnostics.cpp:11`). With the ESP polling, quadrants show settled
pieces on black with white edges; after 3 s of bus silence they idle-breathe. So
"boards stay in debug state until the game starts" costs nothing: send no
lighting commands until Start, and `lighting.clear` + restored config keys put it
back afterwards.

## 5. Coordinates — one convention, stated loudly

```
device square index  ==  shakmaty Square as u8  ==  FEN index with a1 = 0
sq = rank * 8 + file      a1 = 0, h1 = 7, a8 = 56, h8 = 63      row-major
```

They already agree (`docs/client-api.md` §Quadrant mapping vs `shakmaty::Square`).
**No conversion anywhere.** `u8::from(square)` and nothing else.

Per-quadrant rotation is already the ESP's job (config key 9). Add one
server-side `board_rotation ∈ {0, 90, 180, 270}`, applied on ingest and on paint,
default 0 — a one-dropdown fix if the board turns out mounted rotated relative to
the game, and it flips occupancy interpretation *and* lighting in one place. Ten
lines, classic demo-day save.

## 6. Protocol

Two new message types on the existing `/ws`. Unknown types are already ignored by
contract, so old clients keep working.

### Server → all clients: `game.state`

Full snapshot on change, coalesced to ≤ 10 Hz, and embedded in `init` as a
top-level `game` field so a browser refresh is free. Full-snapshot broadcasting
matches the platform's existing philosophy — snapshots supersede, no incremental
sync bugs.

```json
{
  "type": "game.state",
  "game_seq": 17,
  "phase": "idle | setup | countdown | playing | awaiting_choice | scoring | finished",
  "device_id": "arcade-chess-001",
  "position": { "id": "a1b2c3", "start_fen": "8/5k2/… w - - 0 1" },
  "fen": "current FEN",
  "turn": "white",
  "ply": 3,
  "max_ply": 10,
  "moves": [{ "uci": "e4d5", "san": "exd5", "by": "sensor | manual | chosen" }],
  "legal_moves": ["d6d7", "d6e7"],
  "setup": { "placed": 6, "needed": 8, "missing": [12, 44], "extra": [13],
             "unknown": [55], "auto_start_in_ms": null },
  "detect": { "mode": "auto | suggest | off", "sensors_live": true,
              "board_synced": true, "mismatch": [],
              "observed": "..+.-?x..………" },
  "choice": { "kind": "capture | promotion | no_match",
              "options": [{ "uci": "e4d5", "san": "exd5", "confidence": "likely" }],
              "prompt": "Which piece was captured?" },
  "eval": { "cp": 34, "win_prob": 0.53, "status": "ok | pending | unavailable",
            "source": "stockfish | material | admin", "depth": 14 },
  "result": { "winner": "white | black | draw", "final_cp": 123,
              "reason": "eval | mate | stalemate | admin" },
  "degraded": ["node2_offline", "engine_unavailable", "bars_unsupported"]
}
```

`detect.observed` is a 64-character string (`.` empty, `+` positive, `-`
negative, `?` uncertain, `x` unknown) — 64 bytes instead of a 600-byte array,
which matters at 10 Hz to every client. `sensors_live` is false when no device is
bound or its snapshot is stale, so the UI says "manual mode" instead of
pretending. `choice` only appears in `awaiting_choice`, `result` only in
`finished`. `degraded` is a product feature, not debug output: it renders as
amber chips and gives the presenter something honest to say when a subsystem
drops.

### Client → server: `game` (admin-gated, same gate as `command`)

```json
{ "type": "game", "action": "new_game", "position_id": "optional", "fen": "optional" }
{ "type": "game", "action": "start" }                    // force-start from setup
{ "type": "game", "action": "move", "uci": "e2e4" }
{ "type": "game", "action": "choose", "uci": "e4d5" }    // resolve awaiting_choice
{ "type": "game", "action": "undo" }                     // revert a ply, re-eval
{ "type": "game", "action": "resync" }                   // board == game state now
{ "type": "game", "action": "set_detect", "mode": "auto | suggest | off" }
{ "type": "game", "action": "mask_square", "square": 27, "masked": true }
{ "type": "game", "action": "set_tunables", "settle_ms": 700 }
{ "type": "game", "action": "set_eval", "cp": 150 }      // eval by decree
{ "type": "game", "action": "set_fen", "fen": "…" }      // overwrite the position — the desync escape when undo can't reconstruct reality
{ "type": "game", "action": "rescore" }                  // re-run the engine on the current position
{ "type": "game", "action": "end", "winner": "white" }   // result by decree
{ "type": "game", "action": "abort" }                    // idle + lighting.clear
{ "type": "game", "action": "bind_device", "device_id": "…" }
{ "type": "game", "action": "set_rotation", "degrees": 180 }
{ "type": "game", "action": "bars_map", "side": 0, "half": 1, "node": 2, "strip": "a", "reversed": true }
{ "type": "game", "action": "bars_test", "node": 2, "strip": "a", "pixel": 3 }
{ "type": "game", "action": "autopilot", "on": true, "interval_ms": 4000 }
```

Replies reuse the existing `error` envelope (`unauthorized`, `invalid_args`); a
success is acknowledged by the next `game.state`.

**Everything is admin-gated**, including Start. The operator's browser remembers
the password in localStorage already, so this costs one login and closes the "any
laptop on the venue wifi can reset the demo" hole. Spectator screens watch
unauthenticated. `GAME_OPEN_CONTROLS=1` relaxes player-facing actions if a second
unauthed tablet at the board turns out to be wanted.

Also `GET /api/game`, mirroring `/api/state`, for curl debugging when the UI is
the thing that's broken.

## 7. Move detection

### 7.1 The asymmetry that makes this tractable

We are not identifying pieces. **We already know the position.** The server holds
the truth in `shakmaty`, so the job is matching a sensor delta against a legal
move list — 10-30 entries in an 8-piece endgame. The board can never tell a rook
from a king; piece identity lives exclusively in the tracked game state.

### 7.2 Observation layer (`game/observe.rs`)

Per bound device, from the relayed event stream, reusing the server's existing
gap handling:

```rust
occ[64]:     Empty | Pos | Neg | Wobble | Unknown
known[64]:   node_online(sq) && !masked[sq]        // NOT snapshot `valid` — see §4
journal:     squares observed momentarily empty or wobbling since the last commit
last_change_ms[64], quiet_since_ms
```

- `board.snapshot` rebuilds everything (authoritative by contract).
- `sensor.changed` applies while `(boot_id, seq)` is contiguous; the server
  already re-requests a snapshot when it isn't.
- `Unknown` = offline quadrant or operator-masked. Unknown squares are **excluded
  from comparison** — they can neither confirm nor deny, and they never
  contribute negative evidence. A dead quadrant degrades detection without
  corrupting it.
- `Wobble` (uncertain) is **sticky**: keep the last occupancy value, mark the
  square unstable. A square flapping forever delays auto-detect and never
  corrupts state.
- Settled = no unmasked square changed *and* nothing is wobbling for `SETTLE_MS`
  (700). A hand over the board holds the state machine open, which is correct.

### 7.3 Setup detection

Target = the ≤ 8 occupied squares of the dealt position.

```
missing = target ∖ observed_occupied     (known squares only)
extra   = observed_occupied ∖ target     (known squares only)
unknown = target ∩ unknown_squares
```

Auto-start when `missing` and `extra` are empty, `unknown.len() <=
UNKNOWN_TOLERANCE` (default 0), and nothing has changed for
`AUTOSTART_STABLE_MS` (1500). Then a 3 s countdown, abortable by any board
change (`auto_start_in_ms` drives the on-screen counter).

At the end of the countdown, **record the polarity of all eight occupied squares
into `pol_tag[64]`** — the per-piece fingerprint, learned for free and carried
with the piece for the rest of the game.

`pol_tag` is a living table, not a one-shot: every committed move migrates the
tag from → to; a capture overwrites the victim's tag with the attacker's; a
promotion relearns from whatever physically landed, since the promoted queen is
a different piece with its own magnet. Each ply records the tag delta it
applied, so `undo` restores the previous table exactly. Without migration the
fingerprint is stale after move one.

**Start** is always enabled and shows what it overrides ("6 of 8 placed · 1
sensor unknown"). A manual start records polarity only for squares that actually
read occupied; the rest stay `None` and simply supply no evidence later.

### 7.4 Matching: settled state, three tiers

**Do not track transitions.** Match *net occupancy across a settled window*.
Players slide, hover, lift the wrong piece and put it back, and knock things
over. Sequence matching drowns in that; settled-state matching makes
lift-attacker-first, lift-victim-first, fumble and put-it-back all invisible.

On settle, compute the expected occupancy of the resulting position for **every
legal move**, and walk three tiers. The cheap tier is provably correct and has no
tunable constants; the tunable tier only ever runs when the hardware has already
lied.

**Tier 1 — exact match.** Compare observed occupancy (known squares only)
against each hypothesis. Exactly one match → commit. Equal to the *current*
position → no-op (a piece was lifted and replaced; polarity flips are invisible
here, which is the point).

This tier is bounded by a clean argument, and it is worth knowing that the
ambiguity is small and enumerable rather than open-ended:

- A quiet move empties `from` and fills `to`. Distinct `(from, to)` pairs give
  distinct occupancy sets, so a quiet move is **unique**.
- Castling changes four squares, en passant three — both **unique**.
- Captures reduce the occupied count by one while quiet moves preserve it, so the
  two classes can never collide.
- The **only** collisions are several legal captures by the same piece (a pawn on
  e4 taking d5 or f5 leaves identical occupancy) and promotion piece choice.

**Tier 2 — resolve a Tier-1 collision.** Two independent discriminators, both
free:

- **The transient journal.** The victim was physically lifted at some point, so
  its square shows a momentary empty or wobble. Pick the candidate whose
  destination appears in the journal.
- **Polarity change.** If the destination's polarity differs from before, a
  *different physical piece* now sits there — the capture is confirmed and named.
  Fires roughly half the time and is decisive when it does. Used only additively:
  a matching polarity is weak confirmation, never a veto, so the occupancy-only
  robustness is preserved.
- Promotion: auto-queen, since occupancy cannot see the choice. Undo + manual
  move covers the crowd-pleasing underpromotion.

If both discriminators are silent → `awaiting_choice`, with two big buttons on
screen. Ten seconds of operator attention, not a broken game.

**Tier 3 — no exact match (the hardware is lying).** This is the case a strict
matcher fails *totally* and *silently* on: one square stuck confidently-occupied
by baseline drift is `valid == true` throughout and poisons every hypothesis for
the whole game. So instead of giving up, score the hypotheses:

```
distance(m) = Σ over known squares where observed ≠ expected(m):
    each disagreeing square                                      +1.0
  except the off-centre pair, counted once, not twice:
    m.to reads empty AND exactly one neighbour of m.to is
    unexpectedly occupied  (magnet at the piece base, sensor
    at the square centre — off-centre placement reads next
    door; polarity ignored on the neighbour)                     +0.5 for the pair
  then one polarity term, skipped for promotions or when
  either tag is unknown:
    pol(m.to) == pol_tag[m.from]                                 −0.5 (floor 0.0)
    mismatch — per §4 an off-centre piece can genuinely read
    inverted, so a mismatch is not evidence against the move     +0.0
```

Purely additive, every term in the same unit — there is exactly one way to
implement it, which matters for constants that cannot be validated before game
time.

**Auto-mask a lying square.** If a square disagrees with expectation across ≥ 2
consecutive settles, it is stuck, not surprising. Mask it automatically, announce
`sensor_27_suspect` in `degraded`, and Tier 1 resumes cleanly on the remaining
known squares — which beats both prompting on every ply forever and leaning on
Tier 3's weights. **Only during `playing`**: during setup a piece on the wrong
square looks identical, and masking it would let a bad build pass.

Accept the best hypothesis when `distance <= 1.0` and the runner-up is at least
`1.0` worse; mark the move `confidence: "likely"`. In `auto` mode it commits and
the UI says so; in `suggest` mode it becomes a one-tap prompt. Anything worse →
`choice{kind: "no_match"}` with the diff highlighted on screen and the offending
squares flashed red on the board.

Worked examples — the two cases Tier 3 exists for:

- *Stuck square* `s`, part of no legal move: the true move's hypothesis
  disagrees with observed occupancy only at `s` → distance 1.0. Any rival move
  also misses its own from/to evidence → ≥ 3.0. The margin holds and the true
  move commits with a badge; the auto-mask above then retires `s` at the next
  settle.
- *Off-centre drop*: `m.to` reads empty, one neighbour unexpectedly filled →
  distance 0.5 → commits with a badge and arms the nudge below.

**A neighbour-credit commit leaves a standing offset** — the game says e4, the
piece physically reads d4 — and every later settle would inherit that
disagreement, eroding the margin ply after ply until the game degrades into
prompts. The offset is therefore never silently absorbed: the screen banners
"nudge the piece onto e4", e4 lights amber, and both persist until observed
occupancy matches the game position again. Detection does not re-baseline
around it — the player fixes it in two seconds, because the board is asking.

Because Tier 3 only runs after Tier 1 has failed, **its constants can be wrong
without breaking the common case** — which matters when they are guesses until
game time.

`detect.mode`:
- `auto` (default) — Tier 1/2 commit silently, Tier 3 commits with a confidence
  badge.
- `suggest` — nothing auto-commits; the board proposes, one tap confirms.
  **Switch here the moment auto misfires on stage.** Still feels magic, cannot be
  wrong.
- `off` — pure click-to-move.

After any commit, undo or `resync`: clear the journal and recompute expected
occupancy. `resync` is the big hammer — "the game state is right, believe the
board matches it now" — for when someone knocks the pieces over and rebuilds.

### 7.5 Where it lands

| Situation | Outcome |
| --- | --- |
| Quiet move, castling, en passant | Tier 1, commits ~50 ms after settling |
| Capture, one legal capture from that square | Tier 1 |
| Capture, polarity flipped | Tier 2, decisive |
| Capture, several from the same piece, victim seen lifted | Tier 2 via journal |
| Capture, journal lost to a seq gap | 2-button prompt |
| One sensor lying | Tier 3, or a prompt; `mask_square` removes it permanently in one click |
| Both endpoints on a dead quadrant | No evidence → the move list, i.e. click-to-move |
| Physically illegal move | `no_match`, squares flashed red, position untouched |
| Two-handed fiddling | Distance too large → prompt |

`infer(expected_position, settled_occupancy, known_mask, journal, pol_tags) →
NoChange | Move(uci) | Ambiguous(options) | Mismatch(squares)` is a pure function
with no I/O. It is the one component that **cannot be debugged live on stage**, so
it gets the unit tests (§13).

### 7.6 Tunables

`SETTLE_MS 700`, `AUTOSTART_STABLE_MS 1500`, `UNKNOWN_TOLERANCE 0`,
`TIER3_MAX_DISTANCE 1.0`, `TIER3_MARGIN 1.0`, `DRAW_BAND_CP 40`. Env vars for the
deploy, `set_tunables` for live changes, all shown in the admin rail. Being able
to change these from a phone at the venue is the highest-value risk mitigation
here.

## 8. Square lighting (`game/paint.rs`)

The server composes a desired board frame and diffs it against the last one sent,
emitting the minimum number of commands. Three capability tiers, chosen per
quadrant automatically:

| tier | requires | square capability |
| --- | --- | --- |
| **Rich** | new AVR firmware (§9) | per-square RGB, full colour language |
| **Basic** | nothing (works today) | one override colour per quadrant + neutralised sensor colour |
| **Dark** | quadrant offline | nothing; screen only |

**Basic tier still delivers the setup experience**, which is the important part:

> Override mask = *only the target squares that are still empty*, in amber. When
> a piece lands, drop that square from the mask so it falls through to the sensor
> colour (both config keys set to one neutral white).
> **Amber = still needed. White = piece detected. No amber left = board built.**

One colour per quadrant, zero firmware change, and self-correcting: pick up a
wrongly placed piece and its target lights amber again. A dead sensor never turns
white, which is honest — that is what Start is for.

| phase | frame |
| --- | --- |
| `idle` | **nothing sent.** Board keeps its debug behaviour |
| `setup` | amber on still-missing targets (rich tier adds red for `extra`) |
| `countdown` | the eight target squares pulse, one frame per second |
| `playing` | last move's from+to in soft blue |
| `awaiting_choice` / `no_match` | candidate destinations flashed; illegal in red |
| `finished` | winner-colour sweep, ≤ 5 frames |
| `abort` | `lighting.clear` + restore config keys 7/8 |

Paint on state change, never per sensor event, plus a 1 Hz re-assert so a stray
probe from the debug console self-heals within a second.

## 9. Edge bars

Two of the four sides carry the **turn indicator**, two the **eval bar**, so both
players see both.

**Eval bar (16 px, tug of war).** `fill = round(16 × win_prob_white)`; pixels
`[0, fill)` in white's colour, `[fill, 16)` in black's. Starts at exactly 8/8 —
the 50/50 the game opens on. Clamped to `[1, 15]` short of mate so the bar never
loses its orientation. Repaints only on commit (≤ 10 times a game). The website's
`EvalBar` renders **16 segments** too, so screen and hardware read identically.

**Turn indicator (16 px).** Solid in the side-to-move's colour, changing only on
turn change. Static, so it costs nothing on the bus.

### 9.1 The firmware change

One new message, delivering bars *and* per-square colour, because you only want
to flash the quadrants once. A bars-only message would leave §4's one-colour
constraint in place permanently.

```
kSetPixels = 0x45
request  : zone:u8, mask:u16le, popcount(mask) × rgb565:u16le      (≤ 35 bytes)
           zone 0 = squares, mask bits 0..15 = local square index
           zone 1 = bar A,   zone 2 = bar B, mask bits 0..7 = bar position
response : zone:u8, mask:u16le
error 1  : length != 3 + 2·popcount(mask), or bits 8..15 set on a bar zone
mask = 0 : clear that zone's override
```

- **AVR** (`lighting.h/.cpp`, ~40 lines): add `square_colour_[16]`,
  `square_colour_mask_`, `bar_[2][8]` — 67 bytes of SRAM. `render()` priority
  becomes identify > per-square colour > legacy `override_mask_` > sensor colour.
  Bars render through the existing `board_map::kEdgePixelForPosition`
  transposition, defaulting to white until a bar zone is first written. Legacy
  `SET_SQUARES` semantics untouched. **Check the PlatformIO RAM figure after
  building.**
- **ESP** (`bus_manager`, `network_commands`): raise `kMaximumQueuedPayload`
  24 → 40 (128 bytes of ESP32 RAM), add `setPixels()`, add `lighting.paint`
  (global squares → per-node zone-0 frames) and `lighting.bar`
  (`{node, strip, pixels: ["rrggbb" × 8]}`). Also add the ESP-only
  `node.config.set {node, key, value}` from §4 — that one needs no AVR change and
  is worth doing on its own.
- **Capability discovery**: the first `node_error code=2` from a node marks it
  Basic tier for the session and adds `bars_unsupported` to `degraded`. Nothing
  else changes; every value the bars carry is already on screen.
- **If the ESP queue bump feels risky under time pressure**, there is a smaller
  variant: a fill-range message `strip, start, count, r, g, b, duration:u16` — 8
  bytes, fits the existing 24-byte cap untouched. Bars only ever need "k of 16 in
  colour A, the rest in B", so two frames per strip covers the eval bar. Cost: a
  second message per strip and no per-square RGB, so §8 stays on Basic tier
  forever. Take this only if the queue change is the thing blocking the flash.

### 9.2 Bar mapping — assume it's wrong

```
bar_map[side 0..3][half 0..1] = { node, strip: A|B, reversed: bool }
```

Ship a guessed default and an assignment tool in the admin rail: **8 buttons**
(one per node × strip) that light that half-bar in a distinct colour, **8
dropdowns** to record which side/half it turned out to be, and a reverse checkbox
each. Two minutes at the venue, and it turns an unknown into a form to fill in.
`bars_test` with a pixel index does single-pixel walking for direction.

### 9.3 Go / no-go

Bars are the only part of this plan needing new AVR firmware, and flashing four
quadrants on flaky hardware is a real risk. Attempt it **only** after cut line B,
and only if a bench quadrant validates the image before the real four are
touched. Wall-clock caveat: it is last in dependency order but needs a flash
cycle and a walking-pixel check, so if it happens at all it must start early
enough to finish.

If it doesn't happen: eval bar and turn indicator live on screen, which they do
anyway. (`node.identify` pulsing a node amber is a zero-firmware hack for turn
indication, but it blinks the square strips too — noted and rejected as too ugly
for anything but desperation.)

## 10. Engine (`game/engine.rs`)

- One `tokio::process` child speaking UCI over pipes, requests serialized through
  an mpsc, one in flight. Crib the parsing from `position-miner/src/verify.rs`
  (`info … score cp|mate`, `bestmove`, `UCI_ShowWDL`).
- Per-ply: `go movetime 400`. Final verdict: `go movetime 2000`.
- **Normalize to white POV** — UCI reports side-to-move POV. Classic sign bug;
  unit-test it. `mate in N` clamps to ±1500 cp for display.
- **Win probability** for the bar, lichess curve:
  `win% = 50 + 50 · (2 / (1 + e^(−0.00368208 · cp)) − 1)`.
  Prefer WDL when the engine reports it (`(win + draw/2)/1000`); the two agree
  closely enough that the bar doesn't jump between sources.
- Every result carries the `game_seq` it was requested at, so an eval for a
  position that has since been undone is dropped rather than displayed.
- Failure handling: spawn failure or a 3 s timeout kills and respawns the child
  with bounded backoff. While down, eval falls back to **material count** via
  shakmaty, labelled `source: "material"` — never silently lie about where the
  number came from. Below that, `set_eval` and `end {winner}` exist.
- Docker: `apt-get install -y stockfish` in the runtime stage of
  `server/Dockerfile` (bookworm ships 15.1, ample at 400 ms). `STOCKFISH_PATH`
  overrides, default `/usr/games/stockfish` with a PATH search fallback.

**Verdict — judge the swing, not the absolute.** `swing = final_cp − start_cp`,
white POV: `swing ≥ +DRAW_BAND_CP` (40) → white, `≤ −40` → black, else draw. Mate
or stalemate during play ends immediately.

The absolute final eval is the wrong number: `arcpos mine --band` defaults to
±30 cp (`main.rs:58`) and `verify` keeps anything within ±40 cp (`verify.rs:88`),
so a dealt position can legitimately sit at +35 before anyone touches it. Judging
the absolute means two players can shuffle for five moves, change nothing, and be
told White won — with no way to explain it. The swing is also the better line on
stage: "Black gained a pawn and a half in five moves". The bar still shows
absolute win probability; it starts near centre because that is what the mining
guarantees, and any residual offset is honest.

## 11. Positions (`game/positions.rs`)

The miner already produces exactly what's needed and already emits JSON, so the
contract with that workstream is one command:

```sh
arcpos dump verified.arcpos --json -n 5000 > positions.json
```

`--json` emits JSON lines with `id`, `fen`, `verified_cp`, `drop_cp` and more
(`position-miner/src/review.rs:51`). **Note `-n` defaults to 20**
(`main.rs:145`) — without raising it you silently get a 20-position file.

- `POSITIONS_PATH` is loaded at startup, accepting a JSON array *or* JSON lines,
  each record needing only `fen`. Unknown fields ignored, malformed lines skipped
  and counted rather than fatal.
- **Embedded fallback**: ~8 hand-checked even endgames compiled into the binary
  via `include_str!`, used when the file is missing, empty or unparseable. Log it,
  don't die. The game mode must not block on the miner finishing.
- Validate each record on load, precisely — "illegal position" is a real
  `shakmaty` concern and worth naming rather than hand-waving:
  1. `Fen::parse` → `into_position(CastlingMode::Standard)`, which is what
     rejects the side *not* to move being in check, i.e. the actual illegality.
  2. ≤ 8 pieces (the miner guarantees it; check anyway).
  3. `!pos.is_game_over()`.
  4. `pos.legal_moves().len() >= 2` — one legal move makes a five-move game
     pointless.
- `new_game` picks uniformly at random avoiding the last few used;
  `position_id`/`fen` args rig a rehearsed position — worth doing for the opening
  game of the presentation.
- **Deployment gotcha:** `position-miner/data/` is gitignored and CapRover builds
  from git, so the deployed container has *only* the embedded fallback unless the
  curated JSON is committed or mounted as a volume. Decide which, tonight.

## 12. Frontend

New route `frontend/src/routes/game/+page.svelte`. **`/` is not modified** — no
regression risk on the working bring-up dashboard, and it stays one tab away for
raw lighting, snapshots, calibration and the bus trace. Two simultaneous
consumers: the **projector** (unauthenticated, readable across a room) and the
**operator's phone/laptop** (authed, admin rail).

- `ws.svelte.ts`: add a `game` field, handle `game.state` in `#onMessage` and
  `init`, add `sendGame(action, extra)`. ~40 lines, no structural change.
- `GameBoard.svelte` — chess-oriented; the existing `Board.svelte` stays
  sensor-oriented. Renders the FEN with **Unicode glyphs** (♔♕♖♗♘♙ — zero assets,
  which matters on the static Cloudflare deploy), plus overlays: last move, setup
  missing/extra/unknown, detection mismatch, legal-target dots from
  `legal_moves`, click-to-move.
- `EvalBar.svelte` — 16 segments (mirroring the hardware), animated, with the cp
  number and a source badge: *stockfish / material / manual*.
- `TurnBanner.svelte` — huge side-to-move indicator plus "Move 3 of 5 — White",
  doubling as the phase banner.
- `SetupPanel.svelte` — target diagram, "6 of 8 placed", per-square hints, Start
  button, auto-start countdown.
- `ChoicePrompt.svelte` — up to three big SAN buttons plus "none of these".
- `AdminRail.svelte` — collapsible, only when `ws.authed`: every `game` action as
  a button, tunable sliders, square-mask toggles (arm, then click a square), bar
  mapping tool, engine status, autopilot, plus node health at a glance.
- `ResultOverlay.svelte` — full-screen winner splash with the final eval and the
  ten moves in SAN.

Manual move entry is not a hidden fallback — it is the same click-to-move UI
whether detection is on or off. Detection just does the clicking for you.

## 13. Testing without hardware

Written blind, so build the things that make it testable. Three pieces, none
optional.

**1. `tools/fake-board.py`** — a websocket client speaking the *device* API on
`/board`: `hello`, snapshots, `sensor.changed` streams with real `boot_id`/`seq`
discipline. Interactive commands: `place 12`, `lift 12`,
`move e2e4` (a realistic sloppy lift/hover/place sequence with randomized
polarity and optional uncertain flickers), `capture e4d5 victim-first|attacker-first`,
`node 2 offline`, `wobble 12`, `stick 12 occupied`, `gap 5`. Driving the real
websocket path — not an in-process shortcut — is what exercises seq-gap recovery,
the snapshot/incremental mix and the exact ESP JSON shapes.

**uv, following `tools/flash-quadrant.py`** — a self-contained PEP 723 script, no
venv to create and no requirements file to keep in sync:

```python
#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.10"
# dependencies = ["websockets"]
# ///
```

Run it as `./tools/fake-board.py ws://localhost:8080/board` (or
`uv run tools/fake-board.py …`). Every Python tool in this plan uses that
convention — no bare `python3`, no `pip install`.

The script comes first because S1 exists to let you test S2 and S3 **as you write
them**, and it can be written while the Rust doesn't compile. *If time allows*,
the same device can be re-implemented in-server (`game/sim.rs`, loopback
WebSocket to its own `/board`), which keeps the transport fidelity while becoming
triggerable from the admin rail **at the venue** — worth having, since the script
needs a terminal. Three snags to plan for if you do: it puts `tokio-tungstenite`
on the critical build path; the loopback connect must carry
`Authorization: Bearer $DEVICE_TOKEN` when that is configured
(`server/src/device.rs`) or it is refused at the upgrade; and `sim.enable` needs
a guard against a real board already being bound, or two devices race.

**2. Unit tests on `infer()`** — table-driven, in the style of the existing
`state.rs` tests. At minimum: quiet move; capture both lift orders; castling; en
passant; ambiguous capture resolved by journal; ambiguous capture resolved by
polarity flip; ambiguous capture → choice; lift-and-replace no-op; polarity-flip
no-op; offline-quadrant masking; a square stuck occupied (Tier 3, then auto-masked on
the second settle); a piece dropped one square off (neighbour credit, then the
nudge persisting until the piece is corrected); `pol_tag` migration across a
commit and restoration across an undo; a hover transient producing nothing;
illegal settle → mismatch; promotion auto-queen; UCI sign normalization; win-prob
curve endpoints.

**3. Autopilot** — `autopilot {on}` steps the server through legal moves every
few seconds with the eval bar tracking. Distinct in purpose from the fake board:
that one is a test fixture, this is the **on-stage rescue** when nothing physical
works, and an attract loop between runs.

**Full rehearsal**: run the presentation script twice against the fake board —
once happy-path, once with injected chaos (node dropped mid-game, ambiguous
capture, a stuck square, Stockfish killed) exercising the admin rail.

## 15. Failure-mode matrix

Acceptance criteria. Every row should be exercised against the fake board before
the demo.

| failure | behaviour |
| --- | --- |
| ESP never connects | `sensors_live: false`, manual mode from the start, game fully playable |
| board connects mid-game | observation resumes on the next snapshot, detection re-arms, no state loss |
| quadrant offline mid-game | its squares Unknown and excluded; detection covers the rest; those moves clicked |
| polarity flip on lift/replace | invisible — Tier 1 is occupancy-only |
| hall flicker / uncertain | sticky + settle window absorbs it; a permanently flapping square delays auto-detect, never corrupts state |
| hand hovering over the board | holds the state machine open; no premature commit, no premature auto-start |
| capture lift ordering | invisible — settled-state matching |
| ambiguous capture | journal, else polarity, else 2-button prompt |
| one sensor stuck confidently wrong | Tier 3 absorbs it; `mask_square` removes it permanently in one click |
| piece read one square off | neighbour credit in Tier 3, then a persistent nudge prompt until corrected; setup shows the diff |
| illegal physical move | zero matches → red squares + on-screen diff; players fix it or the admin enters reality |
| seq gap / device reboot | existing snapshot-heal path; game re-diffs against the fresh snapshot; worst case one `resync` |
| whole board rotated | `set_rotation`, live, fixes occupancy and lighting together |
| Stockfish dead | material eval, labelled; `set_eval` / `end` as the last word |
| bars unsupported or unflashed | skipped after one `node_error`; chip `bars_unsupported`; screen unaffected |
| bars mapped wrong | fixed in the mapping tool, live, no redeploy |
| browser refresh / projector hiccup | free — full state in `init` |
| server restarts mid-game | survivable for ~30 lines: write `game.state` to `/tmp/arcade-game.json` on every phase change and restore on boot. Worth having, since a redeploy is how you'd fix anything else. Without it, restart the round — it's a 5-minute game |
| everything hardware dead | `autopilot` plays both sides with a live eval bar; the script survives |

## 17. Decisions assumed — flag any you disagree with

1. **"Even position" = engine-level but sharp** (`verified_cp ≈ 0`, large
   `drop_cp`), which is what the miner already produces. Not "equal material".
2. **10 plies**, starting with the dealt FEN's side to move, which may be black.
3. **Server-authoritative, in-memory, single active game**, bound to one
   `device_id`; other boards stay in debug.
4. **All game actions admin-gated**, including Start — so whoever presses it must
   be on the authed device. `GAME_OPEN_CONTROLS=1` relaxes that.
5. **`/` untouched**; the game lives at `/game`.
6. **One AVR change** (`kSetPixels`), strictly optional, discovered at runtime per
   quadrant. Everything else is ESP-only or no firmware at all.
7. **Draw band 40 cp.**
8. No clocks, no per-turn timer, one game at a time. `clock-taine` isn't wired to
   the ESP and stays out of scope.
